# Testbench Standardization & AI Agent Workflow Guide

This document outlines the strict architecture and workflow for SystemVerilog testbenches generated by AI Agents. The goal is to ensure highly reliable, deadlock-free, and automated verification loops.

**Specification Language (RFC 2119):** The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHOULD", "MAY" are to be interpreted as described in RFC 2119. This guide is the default baseline for single-module SystemVerilog testbenches (standard IP blocks, peripherals, crypto accelerators, datapaths, processors), unless an existing verification environment mandates a UVM architecture.

## 1. Automated Validation Loop & Agent Workflow
The AI Agent MUST follow a strict cycle for testbench generation and validation:
1. **Project & DUT Discovery:** Search the project directory to locate the target module and real interfaces.
2. **Test Plan Design:** Define Edge cases, Directed scenarios, and Randomized tests based on the DUT's functionality.
3. **Generation:** Write the testbench strictly adhering to the structure in this guide.
4. **Compile $\rightarrow$ Simulate $\rightarrow$ Analyze $\rightarrow$ Fix:** The agent must run the simulation. If compilation fails or the simulation hangs, the agent must parse the logs, analyze the root cause, apply fixes, and re-run until a clean pass is achieved.

### 1.1 The Bounded Fix Contract
* **Retry Limit:** The auto-fix loop MUST NOT exceed a predefined iteration limit (RECOMMENDED: 3 to 5 attempts). If compile, elaboration, or simulation errors persist beyond this limit, the agent MUST halt and report the status as `UNRESOLVED: EXCEEDED_RETRY_LIMIT` instead of looping forever.
* **The Rule of Immutability (CRITICAL):**
  * The agent MUST NOT modify the original RTL source files under test to make a testbench pass.
  * The agent MUST NOT weaken, comment out, or alter golden reference functions, expected values, pass criteria, or checks to force a passing run. A discrepancy between RTL behavior and the reference is a DUT defect or a specification mismatch; it must be reported, not hidden. (A documented, behavior-preserving RTL adaptation for a tool limitation, such as the `XSIM 43-3254` mirror arrays in section 9, is allowed only if it is explicitly recorded.)
* **Failure Preservation:** When a failure occurs, the agent MUST preserve the failing seed, the compile/simulation logs, and the CSV/waveform artifacts for offline triage. Never delete the evidence of a failed run.

## 2. RTL-Grounded Generation (Zero Hallucination Policy)
**CRITICAL:** ALL signals, resets, memories, internal paths, and expected criteria MUST be extracted from the actual project sources.
* **DO NOT guess or hallucinate** any module names, port directions, or internal signal paths.
* **Search Path:** Always scan the Vivado project structure (e.g., `**/*.srcs/sources_1/imports/**/*.v` or `**/*.srcs/**/*.v`) to read the exact RTL before writing the testbench.
* **Probe Paths:** If an internal probe path cannot be resolved from the RTL hierarchy, the agent MUST omit that probe or move the observation point to a verified interface boundary. Never invent a hierarchical path.

### 2.1 Structural vs. Behavioral Discovery
Keep the two kinds of discovery separate:
* **Structural (from RTL):** module names, ports, directions, widths, parameters, reset scheme (active-high/low, sync/async), instance hierarchy.
* **Behavioral (from specification, golden model, or known-answer vectors):** transaction semantics, handshake rules, latency, and the expected numeric outputs used by the scoreboard. Expected values MUST come from an independent reference (equations, reference model, or published test vectors) - never from copying what the DUT produced.
* **Ambiguity Handling:** If a functional criterion or expected output is ambiguous or undocumented, the agent MUST declare an `INSUFFICIENT_SPECIFICATION` exception and ask, instead of inventing expected values.

## 3. Mandatory Testbench Architecture

The testbench MUST be structured sequentially using the following sections:

### 3.1 Parameters, Clock and Signals
* Define all parameters explicitly.
* Declare DUT inputs as `logic` and outputs as `wire`.
* **Clock Initialization:** The clock MUST be initialized to `0` inside an `initial` block to prevent `X` states.
  *(Example: `initial begin clk_i = 1'b0; forever #(CLK_PERIOD/2) clk_i = ~clk_i; end`)*

### 3.2 DUT Instantiation
* Instantiate the DUT using explicit, named port connections (e.g., `.clk_i(clk_i)`).
* Check port width compatibility based on the extracted RTL.

### 3.3 Initialization and Reset
* Initialize all inputs to known values (`0` or tie-offs) at time zero.
* Execute a clean reset sequence based on the RTL's requirements (e.g., active-high or active-low, synchronized to clock).
* Prepare and preload instruction/data memories.

### 3.4 Drivers and Tasks
* Encapsulate bus transactions (e.g., AXI read/write) in `task` blocks.
* **Deadlock Prevention:** Never assume signals like `awready` and `wready` assert in the exact same cycle. Avoid rigid waits like `wait(awready && wready)`. Write flexible tasks that independently monitor handshakes.
* **4-State Safe Handshakes (CRITICAL):** Handshake and status signals must never be tested with loose truthiness such as `if (ready)` or `while (!ready)`, because that treats `1'bx` and `1'bz` ambiguously. All handshake polling MUST use strict case equality (`=== 1'b1` / `!== 1'b1`), and signals MUST be sampled on the active clock edge, never in unclocked zero-delay loops.
* **Bounded Polling Pattern:** Every handshake wait MUST be bounded by a cycle counter that increments an error counter and exits the task cleanly on timeout:

```systemverilog
task automatic wait_for_handshake(ref logic clk, ref logic ready_sig,
                                  input int max_cycles, output bit ok);
  int timeout_cnt = 0;
  ok = 1'b0;
  while (ready_sig !== 1'b1) begin
    @(posedge clk);
    timeout_cnt++;
    if (timeout_cnt >= max_cycles) begin
      $display("[%0t] TB_TIMEOUT: handshake hung (val=%b) for %0d cycles",
               $time, ready_sig, max_cycles);
      return;
    end
  end
  ok = 1'b1;
endtask
```

### 3.5 Monitors and Signal Probes
* Observe external interfaces and required internal state signals.
* Use hierarchical probing (Spy signals) extracted directly from the RTL files.
  *(Example: `wire [31:0] spy_pc = u_dut.internal_core.pc_reg;`)*

### 3.6 Scoreboard and Assertions
* Implement logic to check functional correctness and protocol compliance.
* Compare actual DUT outputs against expected results on-the-fly where possible.
* **Driving is not verification:** pushing transactions into the DUT does not prove anything. For every driven stimulus the scoreboard MUST capture the DUT response on a verified handshake, compare it against the independent expected value, and account for it.
* **Non-zero check enforcement:** a run MUST NOT pass if the check counter is zero. The final report must require `errors == 0 && checks > 0 && tests_done`, so a testbench whose checking code silently never executes fails immediately instead of passing vacuously.

### 3.7 CSV Logger
* Open a CSV file (`$fopen`) and write a header row defining the column contracts.
* Log critical data (Time, Cycle, PC, internal states, Data payloads) on every active clock edge.
* The sampling time and format must remain consistent.

### 3.8 Test Scenarios & Seed Management
The test flow must include distinct execution phases:
1. **Reset Verification:** After reset, check the default/quiescent state (expected outputs idle, no result beats, no valid strobes) before sending any transaction.
2. **Directed & Edge-Case Tests:** Explicitly inject maximum bounds, zeroes, alternating patterns (`0xAAAAAAAA`, `0x55555555`), and simultaneous operations to test architectural limits.
3. **Negative / Rejection Tests:** Inject invalid opcodes, unsupported lengths, or illegal protocol transitions and prove the DUT rejects them gracefully (no accept, no response, no lock-up).
4. **Randomized Tests:** Use `$urandom` or `$urandom_range()` for **Data Payloads and Operands ONLY**.
   * *WARNING:* DO NOT randomize Instruction Opcodes (this will cause Illegal Instruction faults). Pick test scenarios from a fixed whitelist of legal encodings and randomize only the payloads.
   * Manage random seeds for reproducibility (e.g., using `$srandom(seed)`), make the seed selectable from the command line (`+seed=<n>`), and print it so every run and its CSV can be reproduced.

### 3.9 Completion, Watchdog and Report
* **Dynamic End Condition:** The simulation must wait for a specific dynamic event (e.g., a `done` flag, a completion flag set by the scenario thread, or a specific memory write).
* **Watchdog Timer (CRITICAL):** To prevent infinite loops (simulation hangs), you MUST wrap the whole test flow in a `fork ... join_any` block paired with a static timeout branch, followed by `disable fork`.
* **Unified Teardown (CRITICAL):** All termination paths must converge on ONE teardown sequence, executed after `disable fork`: close every open file handle, print a final summary banner, decide PASS/FAIL with the full criteria (`errors == 0 && checks > 0 && tests_done`), then `$finish` on pass or `$fatal(1, ...)` on fail (a nonzero exit code makes batch runs and CI fail loudly). A watchdog expiry must print the deadlock time, set the failure flag, and still reach this teardown so a hung run always leaves a complete report behind.

## 4. Structural Template Summary

The generated SystemVerilog file MUST map precisely to this skeleton. It is a complete, executable reference implementation: clock initialized to 0, hierarchical probes, a golden reference function, a CSV logger with a header contract, a command-line seed, 4-state safe bounded handshake tasks, a `fork`/`join_any` watchdog, and a single unified teardown that prints one summary banner and exits with a nonzero code on failure:

```systemverilog
`timescale 1ns / 1ps

module tb_standard_generalized;

    // ----------------------------------------------------
    // 1. Parameters & Clock/Reset Declarations
    // ----------------------------------------------------
    localparam CLK_PERIOD          = 10;
    localparam WATCHDOG_TIMEOUT_NS = 500_000;
    localparam DATA_WIDTH          = 32;

    logic clk;
    logic rst_n;

    // ----------------------------------------------------
    // 2. DUT Interface Signals & Hierarchical Probes
    // ----------------------------------------------------
    logic                  tb_req_valid;
    logic [DATA_WIDTH-1:0] tb_req_data;
    wire                   dut_req_ready;
    wire                   dut_resp_valid;
    wire  [DATA_WIDTH-1:0] dut_resp_data;

    // Hierarchical Spy Probes (extracted directly from verified RTL sources)
    wire [3:0] spy_fsm_state = u_dut.current_state;

    // ----------------------------------------------------
    // 3. Test Control, Telemetry, and Accounting
    // ----------------------------------------------------
    int error_count      = 0;
    int check_count      = 0;
    int cycle_count      = 0;
    int random_seed      = 1;
    bit test_completed   = 1'b0;
    bit watchdog_tripped = 1'b0;
    int log_file;

    // Golden reference model function (derived from the spec, not from the DUT)
    function automatic logic [DATA_WIDTH-1:0] compute_golden(input logic [DATA_WIDTH-1:0] in_data);
        return in_data ^ 32'hA5A5_A5A5; // example expected transformation
    endfunction

    // ----------------------------------------------------
    // 4. Clock Generation (strict initialization to 0)
    // ----------------------------------------------------
    initial begin
        clk = 1'b0;
        forever #(CLK_PERIOD / 2) clk = ~clk;
    end

    // ----------------------------------------------------
    // 5. DUT Instantiation (explicit named mapping)
    // ----------------------------------------------------
    dut_top #(
        .DATA_WIDTH(DATA_WIDTH)
    ) u_dut (
        .clk_i       (clk),
        .rst_ni      (rst_n),
        .req_valid_i (tb_req_valid),
        .req_data_i  (tb_req_data),
        .req_ready_o (dut_req_ready),
        .resp_valid_o(dut_resp_valid),
        .resp_data_o (dut_resp_data)
    );

    // ----------------------------------------------------
    // 6. CSV Logger Block (one row per active clock edge)
    // ----------------------------------------------------
    always @(posedge clk) begin
        if (log_file != 0 && rst_n === 1'b1) begin
            $fdisplay(log_file, "%0t,%0d,%b,%h,%b,%b,%h,%h",
                      $time, cycle_count, tb_req_valid, tb_req_data,
                      dut_req_ready, dut_resp_valid, dut_resp_data, spy_fsm_state);
            cycle_count++;
        end
    end

    // ----------------------------------------------------
    // 7. Bounded, 4-State-Safe Transaction Tasks
    // ----------------------------------------------------
    task automatic drive_and_check(
        input  logic [DATA_WIDTH-1:0] data,
        input  int                    timeout_cycles = 100
    );
        int cnt = 0;
        logic [DATA_WIDTH-1:0] expected_data;
        expected_data = compute_golden(data);

        // A. Synchronous drive on the clock edge
        @(posedge clk);
        tb_req_valid <= 1'b1;
        tb_req_data  <= data;

        // B. Bounded, 4-state-safe request handshake poll
        @(posedge clk);
        while (dut_req_ready !== 1'b1) begin
            cnt++;
            if (cnt >= timeout_cycles) begin
                error_count++;
                $display("[TB_ERROR] Timeout waiting for req_ready (val=%b) at %0t",
                         dut_req_ready, $time);
                tb_req_valid <= 1'b0;
                return;
            end
            @(posedge clk);
        end
        tb_req_valid <= 1'b0;
        tb_req_data  <= '0;

        // C. Bounded, 4-state-safe response acquisition
        cnt = 0;
        while (dut_resp_valid !== 1'b1) begin
            cnt++;
            if (cnt >= timeout_cycles) begin
                error_count++;
                $display("[TB_ERROR] Timeout waiting for resp_valid (val=%b) at %0t",
                         dut_resp_valid, $time);
                return;
            end
            @(posedge clk);
        end

        // D. Active output comparison (driving is not verification)
        check_count++;
        if (dut_resp_data !== expected_data) begin
            error_count++;
            $display("[TB_MISMATCH] Data error at %0t! Got: 0x%08h, Expected: 0x%08h",
                     $time, dut_resp_data, expected_data);
        end
    endtask

    // ----------------------------------------------------
    // 8. Unified Teardown Procedure (single exit path)
    // ----------------------------------------------------
    task automatic finalize_simulation(input bit is_watchdog);
        if (log_file != 0) begin
            $fclose(log_file);
            log_file = 0;
        end

        $display("=======================================================");
        $display(" VERIFICATION SUMMARY");
        $display("=======================================================");
        $display(" Simulation Time   : %0t", $time);
        $display(" Cycles Executed   : %0d", cycle_count);
        $display(" Checks Performed  : %0d", check_count);
        $display(" Errors Observed   : %0d", error_count);
        $display(" Completion Status : %s",
                 is_watchdog ? "DEADLOCK / TIMEOUT" : (test_completed ? "COMPLETED" : "INCOMPLETE"));
        $display("=======================================================");

        if (is_watchdog || error_count > 0 || check_count == 0 || !test_completed) begin
            $display("== TEST FAILED == Verification criteria not met.");
            $fatal(1, "Terminating with non-zero exit code.");
        end else begin
            $display("== TEST PASSED == All scenarios verified successfully.");
            $finish;
        end
    endtask

    // ----------------------------------------------------
    // 9. Main Execution Flow with Guarded Watchdog
    // ----------------------------------------------------
    initial begin
        // A. Seed & telemetry configuration
        if ($value$plusargs("seed=%d", random_seed)) begin
            $display("[TB] Setting random seed: %0d", random_seed);
        end
        $srandom(random_seed);

        log_file = $fopen("simulation_trace.csv", "w");
        if (log_file == 0) $fatal(1, "[TB] FATAL: Failed to open CSV trace file.");
        $fdisplay(log_file, "Time,Cycle,ReqValid,ReqData,ReqReady,RespValid,RespData,SpyState");

        // B. Deterministic reset phase, inputs quiescent
        rst_n        = 1'b0;
        tb_req_valid = 1'b0;
        tb_req_data  = '0;
        repeat (5) @(posedge clk);
        rst_n        = 1'b1;
        repeat (2) @(posedge clk);

        // C. Guarded test execution
        fork
            // Thread 1: scenario execution and active verification
            begin
                // Scenario 1: directed boundary and edge cases
                drive_and_check('0);
                drive_and_check({DATA_WIDTH{1'b1}});
                drive_and_check(32'h5555_5555);
                drive_and_check(32'hAAAA_AAAA);

                // Scenario 2: constrained-random stimulus (payloads only)
                for (int i = 0; i < 50; i++) begin
                    drive_and_check($urandom());
                end

                // Dynamic completion flag
                test_completed = 1'b1;
            end

            // Thread 2: global watchdog backstop
            begin
                #(WATCHDOG_TIMEOUT_NS);
                $display("[FATAL] Global Watchdog expired at %0t; simulation deadlocked.", $time);
                watchdog_tripped = 1'b1;
            end
        join_any
        disable fork;

        // D. Unified teardown (single PASS/FAIL exit path)
        finalize_simulation(watchdog_tripped);
    end

endmodule
```
## 5. File Placement and Vivado Project Integration

A testbench must exist as a **real file inside the Vivado project directory**. Referencing a file outside the project (by path reference) is not acceptable, because the project then depends on a location that Vivado does not own and the run products do not clearly map to a source.

The two-copy rule:

1. **Source of truth:** `Source Codes/Sim/<project>/<tb_name>.sv` - edit here.
2. **Project copy:** `<project>.srcs/sim_1/imports/<project>/<tb_name>.sv` - this is the copy Vivado compiles; refresh it after every edit.

Keep the two identical and prove it with a hash check after copying:

```powershell
Copy-Item "Source Codes\Sim\<project>\<tb_name>.sv" `
          "Vivado\<project>\<project>.srcs\sim_1\imports\<project>\<tb_name>.sv" -Force
(Get-FileHash "Source Codes\Sim\<project>\<tb_name>.sv" -Algorithm MD5).Hash
(Get-FileHash "Vivado\<project>\<project>.srcs\sim_1\imports\<project>\<tb_name>.sv" -Algorithm MD5).Hash
```

Register the project copy in the `<project>.xpr` inside the `sim_1` fileset (hand-edit the XML and validate it, or use Vivado Tcl). Example for the cup project:

```xml
<FileSet Name="sim_1" Type="SimulationSrcs" RelSrcDir="$PSRCDIR/sim_1">
  <Filter Type="Srcs"/>
  <File Path="$PSRCDIR/sim_1/imports/HORCRUX-cup/tb_horcrux_wrapper.sv">
    <FileInfo>
      <Attr Name="ImportPath" Val="$PPRDIR/../../Source Codes/Sim/HORCRUX-cup/tb_horcrux_wrapper.sv"/>
      <Attr Name="ImportTime" Val="1792069200"/>
      <Attr Name="UsedIn" Val="simulation"/>
    </FileInfo>
  </File>
  <Config>
    <Option Name="DesignMode" Val="RTL"/>
    <Option Name="TopModule" Val="tb_horcrux_wrapper"/>
    <Option Name="TopLib" Val="xil_defaultlib"/>
    <Option Name="TopAutoSet" Val="FALSE"/>
    ...
```

Rules for the registration:

* `UsedIn` is `simulation` only - a testbench is never synthesized.
* The **simulation top** (`TopModule` in `sim_1`) is the testbench; the **design top** in `sources_1` stays the DUT wrapper. Never mix the two.
* After editing the XML, validate it before opening Vivado:

```powershell
try { [xml]$x = Get-Content "Vivado\<project>\<project>.xpr" -Raw; "XML VALID" }
catch { "XML INVALID: $_" }
```

**Preferred registration mechanism: Vivado Tcl.** Hand-edited XML works (it is what the cup project uses) but is prone to schema mistakes; when Vivado is available, registering through Tcl is safer and produces the same physical copy, because `add_files` imports the file into `<project>.srcs/sim_1/imports/...` automatically:

```tcl
add_files -fileset sim_1 -norecurse {C:/<abs>/Source Codes/Sim/<project>/<tb_name>.sv}
set_property used_in_synthesis false [get_files -of_objects [get_filesets sim_1] */<tb_name>.sv]
set_property top <tb_name> [get_filesets sim_1]
update_compile_order -fileset sim_1
```

Either way, the acceptance criteria are the same: the file physically exists under `.srcs/sim_1/imports/`, its `UsedIn` is simulation only, `sim_1` top is the testbench, `sources_1` top is unchanged, and the two copies hash-identical.

## 6. Running the Simulation from the Command Line (Vivado 2019.2)

Use a batch Tcl script so the whole compile-elaborate-simulate flow is reproducible and does not depend on GUI clicks:

```tcl
# run_<project>_sim.tcl
open_project {C:/<absolute/path>/Vivado/<project>/<project>.xpr}
update_compile_order -fileset sources_1
update_compile_order -fileset sim_1
set_property -name {xsim.simulate.runtime} -value {all} -objects [get_filesets sim_1]
launch_simulation -mode behavioral
close_sim
close_project
```

Run it from PowerShell:

```powershell
& "C:\Xilinx\Vivado\2019.2\bin\vivado.bat" -mode batch `
  -source "C:\temp\run_<project>_sim.tcl" `
  -log   "C:\temp\vivado_batch.log" `
  -jou   "C:\temp\vivado_batch.jou"
```

Critical details, each learned from a real failure:

* `set_property xsim.simulate.runtime all` is **mandatory**. Without it Vivado generates `run 1000ns`, and a testbench that needs more than 1000 ns is silently cut short without reaching its PASS/FAIL report.
* One batch run performs three separate stages, each with its own log (see section 7): compile (`xvlog --incr --relax -prj ...`), elaborate (`xelab ... --snapshot <tb>_behav`), simulate (`xsim <snapshot> -tclbatch ...`).
* The simulation working directory is `Vivado/<project>/<project>.sim/sim_1/behav/xsim/`. Any CSV the testbench opens with a relative `$fopen` name lands there, and the `$finish` message in `simulate.log` shows which testbench file was actually compiled (it should be the `.srcs` copy - if it shows another path, the project is not compiling what you think).
* Random seeds are passed as a plusarg, for example `+seed=7` in a custom tclbatch; the testbench must print the seed so every run and its CSV are reproducible.
* In the Vivado GUI the same flow is Project Manager -> Run Simulation -> Run Behavioral Simulation.

## 7. Reporting: Stages and Evidence

Report the three stages **separately**, and only claim a stage passed after reading its log:

| Stage | Command Vivado runs | Evidence file | Pass criterion |
| ----- | ------------------- | ------------- | -------------- |
| Compile | `xvlog --incr --relax -prj <tb>_vlog.prj` | `compile.log` (and the Vivado console) | every file analyzed, no `ERROR` |
| Elaboration | `xelab ... --snapshot <tb>_behav <lib>.<tb> <lib>.glbl` | `elaborate.log` | snapshot built; only known benign warnings (section 9) |
| Behavioral simulation | `xsim <snapshot> -tclbatch <tb>.tcl` | `simulate.log` | testbench summary line with `errors=0`, final `== TEST PASSED ==`, and `$finish` reached |

Check all three logs mechanically:

```powershell
$d = "Vivado\<project>\<project>.sim\sim_1\behav\xsim"
foreach ($f in @("compile.log","elaborate.log","simulate.log")) {
  $hits = @(Select-String -Path "$d\$f" -Pattern "ERROR|CRITICAL")
  $label = if ($hits.Count -gt 0) { "$($hits.Count) ERROR/CRITICAL lines" } else { "clean" }
  "$f : $label"
  foreach ($h in $hits) { "   " + $h.Line.Trim() }
}
```

**Generic Acceptance Checklist.** Beyond the three compile stages, a run may only be declared successful when ALL of these independent gates pass:

| Gate | Evidence | Pass criterion |
| ---- | -------- | -------------- |
| 1. Compilation | `compile.log` | zero `ERROR`, zero syntax/type errors |
| 2. Elaboration | `elaborate.log` | snapshot built, only whitelisted benign warnings (section 9) |
| 3. Simulation run | `simulate.log` | reached `$finish` gracefully, no crash or illegal memory access |
| 4. Watchdog gate | summary line | `tests_done=1` (watchdog branch never fired) |
| 5. Scoreboard gate | summary line | `errors=0` AND `checks>0`, every driven transaction has a verified response |
| 6. Artifact gate | CSV file | file closed, header contract intact, row count matches the executed cycles/transactions |

The mere presence of `$finish`, or the absence of the word "ERROR", is not proof. Evidence must be cross-checked across all six gates.

The testbench itself must print one machine-readable summary line, for example:

```text
TB_SUMMARY results=12 checks=76 errors=0 tests_done=1 csv_rows=71
== TEST PASSED ==
```

`results` counts result beats, `checks` counts every comparison performed, `tests_done` shows the dynamic end condition was reached (0 means the watchdog fired), `csv_rows` links the run to the CSV file. A clean pass means: summary line `errors=0`, `tests_done=1`, and three clean logs.

## 8. CSV Log Contract and Offline Fact-Check

The CSV is the permanent evidence of a run: it can be re-checked later without rerunning the simulator, and it exposes internal state, not just the DUT pins.

Contract:

* Open with `$fopen("name.csv","w")` at time 0 and **check the returned descriptor** - if it is 0, abort with `$fatal` (a run without its evidence file must never pass). Write the header row immediately: the header is the column contract of the file.
* Write **one row per active clock edge** (`always @(posedge clk)`), always sampled at the same point. Group the columns: time/cycle, reset, input-side handshake and payloads, output-side handshake and payloads, then the `spy_*` internal probes. Full-cycle logging suits pipelined designs and trace inspection; for transaction-level IPs with very long runs, logging only on completed handshakes (`valid === 1'b1 && ready === 1'b1`) may be configured to keep file sizes sane - state which mode the CSV uses.
* Probe signals must be hierarchical paths **read from the actual RTL files**, never guessed (section 2). Example from the cup project:

```systemverilog
wire        spy_done  = dut.horcrux_top_i.done;
wire [6:0]  spy_insn  = dut.horcrux_top_i.select_insn;
wire [4:0]  spy_rd_ex = dut.horcrux_top_i.rd_excom;
wire [31:0] spy_rs1   = dut.horcrux_top_i.rs_values.rs1_0;
wire [31:0] spy_rd_v  = dut.horcrux_top_i.rd_values.rd1;
```

* Print the CSV name and the seed in the run transcript, and keep an expected-results table (test name, time, expected data, id, rd) next to the testbench.

Offline fact-check recipes (PowerShell, from the repository root):

```powershell
$csv = Import-Csv "Vivado\<project>\<project>.sim\sim_1\behav\xsim\<tb>_log.csv"

# Reset window: first rows rst_ni=0, then rst_ni=1
$csv | Select-Object -First 5 time_ns, cycle, rst_ni

# Every input handshake - count must match the number of issued transactions
$csv | Where-Object { $_.issue_valid -eq "1" -and $_.accept -eq "1" }

# Every output beat - count and values must match the expected-results table
$csv | Where-Object { $_.result_valid -eq "1" } |
  ForEach-Object { "t=$($_.time_ns) data=$($_.result_data) id=$($_.result_id) rd=$($_.result_rd)" }

# Handshake completeness: every result beat row must also show ready=1 and the internal done flag
$csv | Where-Object { $_.result_valid -eq "1" -and ($_.result_ready -ne "1" -or $_.spy_done -ne "1") }
```

The last query returning **zero rows** is the important invariant: no result was ever dropped or left unconsumed, and the internal done flag agrees with the interface in every beat.

Two sampling facts that look like bugs but are not:

* **NBA scheduling:** `$fdisplay` runs in the active region of the clock edge, while non-blocking assignments update in the NBA region of that same edge. A signal updated by `<=` on an edge is therefore recorded with its pre-update value in that row and appears with the new value in the *subsequent* row. The offline parser must account for this.
* `x` values before and during the first reset edge are normal uninitialized transients, not protocol violations; after reset everything must be defined.

## 9. Known Vivado XSim 2019.2 Issues and Workarounds

* **`XSIM 43-3254` ("Could not find hier sig handle")** when procedural code reads a package array with a runtime index (e.g. `CoproInstr[i].resp.accept` inside a `for` loop in an `always_comb`). Workaround: mirror the constant table into signal arrays with constant genvar indices and read the mirrors:

```systemverilog
logic tbl_accept [NbInstr];
for (genvar j = 0; j < NbInstr; j++) begin : gen_mirror
  assign tbl_accept[j] = CoproInstr[j].resp.accept;
end
// then read tbl_accept[i] with a runtime index - same values, no XSIM 43-3254
```

  The decode behavior is unchanged; verify the mirrored values equal the table values.
* **`XSIM 43-4100` timescale warnings** appear when the testbench declares `` `timescale `` but the RTL modules do not. They are benign; do not add timescales to RTL just to silence them.
* **Standalone `xvlog` needs `--sv` for `.sv` files.** The project flow sets file types automatically, so a standalone CLI check must add the flag itself.
* **Verified as supported** in XSim 2019.2: `$srandom(seed)`, `$urandom_range(max,min)`, `$value$plusargs`, `$fopen/$fdisplay/$fclose`, `$test$plusargs`, `$dumpfile/$dumpvars`, hierarchical references in continuous assignments, `string` task arguments, and `fork/join_any` with `disable fork`.
* **Prefer ASCII-only paths.** A non-ASCII path has caused a file-resolution failure in this tool flow before.
* `$fatal(1, ...)` on test failure gives a nonzero simulator exit code, which makes the batch run fail loudly - use it instead of a silent `$finish` for a failed test.
